# 确任 MVP 启动方案

## 1. 目标

这份文档不是替代 `readme.md` 的完整 PRD，而是把它收敛成一份适合启动研发、设计和排期的执行版本。

首要目标只有一个：

先上线一个能跑通“发布任务/交换 -> 报名申请 -> 沟通 -> 生成订单 -> 完成评价”闭环的移动端产品。

线下门店、逛逛内容流、主理人机制、城市节点活动，都保留在后续版本，不进入首个 MVP。

## 2. 首版产品定义

### 2.1 一句话版本

一个围绕轻任务悬赏和技能交换的同城协作 App。

### 2.2 首版只解决的事情

用户可以：

- 用手机号注册登录
- 完善个人资料与技能标签
- 发布任务
- 发布交换
- 浏览列表和详情
- 申请任务/交换
- 与对方聊天沟通
- 生成订单
- 完成服务并互评
- 发起举报

### 2.3 首版明确不做

- 搭子模块（暂缓）
- 逛逛内容流
- 复杂推荐算法
- 会员体系
- 主理人机制
- 线下门店联动
- 多城市扩张
- 企业任务
- 复杂钱包体系

## 3. 为什么这样收敛

`readme.md` 的完整方向是“任务 + 交换 + 内容 + 线下延展”，但真正决定产品能不能活下来的，是最核心交易闭环是否成立。

MVP 要先验证三件事：

- 有没有人愿意发布真实需求
- 有没有人愿意接轻量任务或进行技能交换
- 平台能不能建立最基本的信任和履约流程

如果这三件事还没验证，太早上重社交模块、内容流和线下，会让团队复杂度快速失控。

## 4. MVP 核心闭环

### 4.1 任务闭环

1. 用户注册并完善资料
2. 发布者创建任务
3. 平台审核通过
4. 接单者提交申请
5. 发布者选择申请人
6. 双方在聊天中确认细节
7. 生成订单
8. 买家支付托管
9. 服务方开始服务
10. 服务方提交完成
11. 买家确认完成
12. 双方评价

### 4.2 交换闭环

1. 用户发布交换信息
2. 平台审核通过
3. 对方申请交换
4. 双方沟通确认
5. 平台生成交换确认单
6. 双方完成后互评

说明：
交换闭环首版不强制接入真实支付，但要有“确认单”和“完成记录”，否则信用体系无法沉淀。

## 9. 推荐技术方案

结合 `readme.md` 的方向，首版建议直接定：

- 客户端：Flutter
- 服务端：NestJS
- 数据库：PostgreSQL
- 缓存：Redis
- 文件存储：S3/OSS 兼容对象存储
- 实时通信：WebSocket
- 管理后台：React + Ant Design

### 9.1 为什么这样定

- Flutter 适合 iOS 和 Android 同时推进
- NestJS 对中后台、权限、模块化和快速迭代很友好
- PostgreSQL 很适合承载结构化业务数据和后续搜索扩展
- React 后台成熟，适合快速搭建审核系统

## 10. 建议的后端模块划分

- `auth`：登录、验证码、鉴权
- `users`：用户资料、标签、认证
- `listings`：任务/交换统一发布模型
- `applications`：申请与接受/拒绝
- `chats`：会话与消息
- `orders`：订单、支付、托管、退款
- `reviews`：评价
- `reports`：举报与风控
- `admin`：审核与后台操作
- `notifications`：站内通知和推送

## 11. 建议的数据建模策略

首版采用统一 `listings` 模型承载任务与交换，依靠 `listing_type` 区分。

推荐枚举：

- `task`
- `exchange`

这样做的好处：

- 列表、搜索、审核、收藏、举报逻辑更统一
- Flutter 端的卡片和详情页组件更容易复用
- 后续扩展 `partner` 或 `feed_story` 时可继续沿统一内容平台思路演进

## 12. 首版最关键的业务规则

### 12.1 发布规则

- 任务和交换都必须经过审核后展示
- 同一用户每天发布条数要有限制
- 涉及敏感词或高风险分类要进入人工复核

### 12.2 申请规则

- 同一用户不可重复申请同一条内容
- 发布者关闭内容后不可再申请
- 被限制信用的用户不能申请高风险或高金额任务

### 12.3 订单规则

- 首版只允许一条任务生成一个有效进行中订单
- 任务被接受后，其他申请自动失效或标记为关闭
- 支付成功后才可进入进行中

### 12.4 评价规则

- 只有已完成订单才能评价
- 双向评价各一次
- 举报成立的订单评价可隐藏

## 13. 首版风控底线

这个项目不是普通内容社区，必须把风控当基础设施。

首版至少要落地：

- 手机号登录
- 敏感词过滤
- 举报入口
- 内容审核状态
- 用户封禁能力
- 订单争议状态
- 黑名单机制

高风险类目直接禁发：

- 情色相关
- 违法违规委托
- 代考代写
- 医疗法律金融承诺型服务
- 未成年人高风险任务
- 人身危险类线下任务

## 16. 冷启动建议

首版不要全国铺开，直接定一个城市。

建议做法：

- 只开放一个城市
- 官方先发 30 到 50 条高质量种子任务
- 优先邀请摄影、简历优化、PPT、宠物照看、语言陪练类供给侧用户
- 交换模块用于降低零成交期的冷启动成本

## 17. 指标看板

MVP 上线后必须每天盯的指标：

- 日活用户数
- 新注册用户数
- 发布数
- 有效申请数
- 发布到首申请时长
- 匹配成功率
- 支付转化率
- 完成率
- 好评率
- 举报率
- 7 日留存

## 18. 当前最值得立即开始的事情

如果我们现在正式开工，建议顺序如下：

1. 先确定技术栈和仓库结构
2. 输出 MVP 页面原型清单
3. 设计数据库 Schema
4. 初始化 Flutter 客户端和 NestJS 服务端
5. 先开发“登录 + 首页列表 + 发布 + 详情”第一条链路

## 19. 我对当前项目的建议结论

这个项目可以做，但必须克制。

最容易失败的方式不是方向不对，而是首版同时想做：

- 任务交易
- 技能交换
- 同城搭子
- 内容社区
- 推荐算法
- 线下门店

真正正确的起步方式是：

先做一个可信的轻任务/交换平台，
等最小履约闭环成立后，再把社交和线下接上去。
